Diagnosis

1 finding(s); most likely: Priority inversion through message passing: rtdemo[1388565] waits on rtdemo[1400834] (high confidence). Kernel trace (1001 ms): 1 of 1 finding(s) confirmed step by step.

Diagnosis 20261123-000334-diagnose-rtdemo, taken 2026-11-23T00:03:34 from 19 thread-state snapshots of the target.

Priority inversion through message passing: rtdemo[1388565] waits on rtdemo[1400834]

high confidence

rtdemo[1388565] 'A-control' (priority 30) waits for a reply from rtdemo[1400834] 'S-server', which serves it at priority 10, while rtdemo[1388565] 'B-worker' (priority 20) keeps the server's CPU. The reply cannot come until the middle-priority work stops, so the high-priority client waits for unrelated work. No mutex is involved.

Evidence

  • In 17 of 19 snapshots rtdemo[1388565] 'A-control' (priority 30) was waiting on a message to process rtdemo[1400834] (REPLY 17), for up to 37 ms.
  • In 17 of those, the server's working thread rtdemo[1400834] 'S-server' ran at priority 10, below its client. On QNX a server thread that receives a message normally runs at the client's priority, so it was not inheriting it.
  • In 4 snapshot(s) a thread between the two priorities had the server's CPU: rtdemo[1388565] 'B-worker' at priority 20 (RUNNING).
  • The deadline report for A-control shows 1069 misses in 121 run(s) of consecutive misses; 121 of those runs started with a long wait for a server's reply (worst 47.1 ms from send to reply; the server's usual answer time is 4.0 ms).

Could not determine

  • Snapshots are instants: 19 were taken, and qbridged reads processes one after another, so client and server are not read at exactly the same moment.
  • Why the server does not inherit the client's priority: qbridge cannot read a channel's flags. _NTO_CHF_FIXED_PRIORITY on the server's channel has this effect; so would a server that sets its own priority after receiving.
  • Which server thread received this client's message, if the server process has several working threads: the snapshot names the process, not the thread.
  • A worst case: finite runs cannot prove the deadline will always be met after a fix.

Suggested fix: Let the server inherit its clients' priority, the QNX default: create its channel without _NTO_CHF_FIXED_PRIORITY (and do not lower the server thread's priority after MsgReceive). The server then works for a client at the client's priority, so a middle-priority thread can no longer delay the reply. If the server must keep a fixed priority, run it above the threads that compete for its CPU.

Recommendation

Keep the change (Let the server inherit its client's priority (create its channel without _NTO_CHF_FIXED_PRIORITY)). Every measured run after it beat every run before it, with the worst case and misses taken first. In this experiment it was rolled back afterwards (for the demo); apply it again in the real code. Re-measure on the real hardware before relying on the deadline, and keep monitoring it in operation.

Limitations

  • These are finite runs (3 before, 3 after). They show the effect of the change on this workload; they do not prove a worst-case response time or that the deadline can never be missed.
  • The target is a QNX 8.0 virtual machine. Virtual-machine timing is noisier than real hardware, and absolute numbers vary between boots; only runs from the same session are compared.
  • Timing check of the target, CPU 0 (2026-11-22T14:57:53): 538 timer wake-ups at a 1 ms period in 10 s; mean lateness 18.17 ms, worst 55.3 ms, 350 wake-ups more than 1 ms late, with nothing else of ours running.
  • Timing check of the target, CPU 1 (2026-11-23T00:02:37): 4935 timer wake-ups at a 1 ms period in 10 s; mean lateness 1.23 ms, worst 9.9 ms, 4917 wake-ups more than 1 ms late, with nothing else of ours running.
  • The workload is a simulated, educational demo. Nothing here is a claim about any automotive, medical or other safety-certified system.
  • Cross-checks: qbridge's statistics agreed with the program's own summary in 6 of 6 runs, and with qbridged's message-passing statistics in 6 of 6 runs.
