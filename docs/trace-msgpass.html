rtdemo[21360661] 'A-control' (priority 30) was blocked (REPLY/SEND) for 801.5 ms. Meanwhile rtdemo[21372930] 'S-server' (priority 10) was ready but held off its CPU for 401.2 ms, mostly by rtdemo[21360661] 'B-worker' (priority 20, 400.2 ms). If the blocked thread was waiting for that thread (a mutex it holds, or a server answering its message), this is a priority inversion.

The trace does not say what a blocked thread waits for (THMUTEX, THSEND and THREPLY name only the waiter), so the lower thread is a candidate, not a proven holder. On a live target, 'qbridge diagnose --trace' reads the mutex owner or the blocked-on server and checks it step by step.
