Diagnosis

1 finding(s); most likely: Priority inversion through message passing: rtdemo[5775362] waits on rtdemo[5783573] (high confidence). Kernel trace (1000 ms): 1 of 1 finding(s) confirmed step by step.

Diagnosis 20261123-171458-diagnose-rtdemo, taken 2026-11-23T17:14:58 from 17 thread-state snapshots of the target.

Priority inversion through message passing: rtdemo[5775362] waits on rtdemo[5783573]

high confidence

rtdemo[5775362] 'A-control' (priority 30) waits for a reply from rtdemo[5783573] 'S-server', which serves it at priority 10, while rtdemo[5775362] 'B-worker' (priority 20) keeps the server's CPU. The reply cannot come until the middle-priority work stops, so the high-priority client waits for unrelated work. No mutex is involved.

Evidence

  • In 14 of 17 snapshots rtdemo[5775362] 'A-control' (priority 30) was waiting on a message to process rtdemo[5783573] (REPLY 14), for up to 40 ms.
  • In 14 of those, the server's working thread rtdemo[5783573] 'S-server' ran at priority 10, below its client. On QNX a server thread that receives a message normally runs at the client's priority, so it was not inheriting it.
  • In 8 snapshot(s) a thread between the two priorities had the server's CPU: rtdemo[5775362] 'B-worker' at priority 20 (RUNNING).
  • The deadline report for A-control shows 878 misses in 110 run(s) of consecutive misses; 110 of those runs started with a long wait for a server's reply (worst 45.4 ms from send to reply; the server's usual answer time is 4.0 ms).

Could not determine

  • Snapshots are instants: 17 were taken, and qbridged reads processes one after another, so client and server are not read at exactly the same moment.
  • Why the server does not inherit the client's priority: qbridge cannot read a channel's flags. _NTO_CHF_FIXED_PRIORITY on the server's channel has this effect; so would a server that sets its own priority after receiving.
  • Which server thread received this client's message, if the server process has several working threads: the snapshot names the process, not the thread.
  • A worst case: finite runs cannot prove the deadline will always be met after a fix.

Suggested fix: Let the server inherit its clients' priority, the QNX default: create its channel without _NTO_CHF_FIXED_PRIORITY (and do not lower the server thread's priority after MsgReceive). The server then works for a client at the client's priority, so a middle-priority thread can no longer delay the reply. If the server must keep a fixed priority, run it above the threads that compete for its CPU.

Kernel trace check

Confirmed by kernel trace: every step was seen.

  • Seen: rtdemo[5775362] 'A-control' blocks waiting for a server (SEND or REPLY). SEND/REPLY 802.2 ms (801.8 ms of it REPLY, the server holding its message) in 182 span(s) in a 1000 ms trace
  • Seen: Meanwhile the server rtdemo[5783573] 'S-server' is ready but not running, below the client's priority (no inheritance). of the 802.2 ms wait the server was RUNNING (doing the work) for 401.1 ms; of the other 401.0 ms it was READY for 401.0 ms (100%), 401.0 ms of it below priority 30
  • Seen: A middle-priority thread holds the server's CPU. rtdemo[5775362] 'B-worker' (priority 20, 400.2 ms), io-sock[188432] 'clock' (priority 21, 0.1 ms), io-sock[188432] 'uma' (priority 21, 0.0 ms) ran for 400.3 ms of the server's 401.0 ms READY time (100%)
  • Seen: Each wait for a reply ends while the server is running (it replies). 100 of 100 completed REPLY waits ended while the server was RUNNING
  • The trace does not name the server a client waits on (THSEND and THREPLY only name the waiting thread, and message events are not recorded); the server's identity comes from the snapshot.
  • The trace covers 1000 ms of the run; it shows what happened in that window only.

The change

Raise the control task's priority from 30 to 50, above everything else, so nothing can delay it. Same binary; the server channel keeps _NTO_CHF_FIXED_PRIORITY.

Recommendation

Do not rely on this change yet. The measurements before and after overlap, so they do not show that it helps. Run more repetitions or a longer workload, or look for another cause.

Limitations

  • These are finite runs (3 before, 3 after). They show the effect of the change on this workload; they do not prove a worst-case response time or that the deadline can never be missed.
  • The target is a QNX 8.0 virtual machine. Virtual-machine timing is noisier than real hardware, and absolute numbers vary between boots; only runs from the same session are compared.
  • Timing check of the target, CPU 0 (2026-11-22T14:57:53): 538 timer wake-ups at a 1 ms period in 10 s; mean lateness 18.17 ms, worst 55.3 ms, 350 wake-ups more than 1 ms late, with nothing else of ours running.
  • Timing check of the target, CPU 1 (2026-11-23T17:08:55): 9992 timer wake-ups at a 1 ms period in 10 s; mean lateness 0.13 ms, worst 1.9 ms, 7 wake-ups more than 1 ms late, with nothing else of ours running.
  • The workload is a simulated, educational demo. Nothing here is a claim about any automotive, medical or other safety-certified system.
  • Cross-checks: qbridge's statistics agreed with the program's own summary in 6 of 6 runs, and with qbridged's message-passing statistics in 6 of 6 runs.
